# ClickBench on the sandbox cluster, 100M rows

**On one c6a.4xlarge query node, smolquery `main@947dfa0` answers all 43
ClickBench queries on the full `hits` table (99,997,497 rows), with a hot sum
of 57.6 s.** Against the published c6a.4xlarge entries that also read
Parquet from S3, it is faster than DuckDB hot and cold, and faster than
ClickHouse cold. ClickHouse is 1.97x faster hot.

| vs. (c6a.4xlarge, reads S3) | hot ratio | cold ratio |
|---|---:|---:|
| duckdb-datalake | 0.67x | 0.87x |
| duckdb-datalake-partitioned | 0.39x | 0.53x |
| clickhouse-datalake | 1.97x | 0.52x |
| clickhouse-datalake-partitioned | 1.80x | 0.58x |

Under 1x means smolquery is faster (geomean per query, ClickBench's metric).

The load took **680.8 s at 146,882 rows/s** (323 MiB/s), from Parquet,
through the HTTP insert route, with zero retries.

## What we compare against

smolquery reads sealed Parquet from S3 through a local file cache. So the
comparison set is ClickBench's object-storage entries, which read the same
`hits` Parquet from a public S3 bucket in eu-central-1, our region:

- `duckdb-datalake`, `duckdb-datalake-partitioned`: DuckDB over httpfs.
  No local cache, so hot is close to cold.
- `clickhouse-datalake`, `clickhouse-datalake-partitioned`: the
  ClickHouse `S3()` table engine, with ClickHouse's own caching on hot runs.

The entries that read local disk (`duckdb`, `clickhouse`, `*-parquet`) are
left out. They measure a different storage model, and a ratio against them
says nothing about this engine.

Published dates: `duckdb-datalake*/results/20260726`,
`clickhouse-datalake*/results/20261004`. Every ratio in this file uses these
dates (`mise run clickbench-report` fetches the latest; ClickBench reran
ClickHouse on 2026-10-04, which moved our ratios against it by up to
0.16x).

## Four passes

All four ran from the in-region load generator, straight to query-0's pod
IP, 3 tries per query, `"fileCache": true`, after deleting the 3 query pods
so every `/cache` started empty. ClickBench also drops the OS page cache; we
did not, but the new pods had not read the table.

| pass | build | job engine | queries | hot sum (s) | median hot (s) | cold sum (s) | vs duckdb-datalake hot / cold | vs clickhouse-datalake hot / cold |
|---|---|---|---:|---:|---:|---:|---:|---:|
| **single** | `947dfa0` | 8GB, 32 threads | **43/43** | **57.6** | 0.859 | **94.2** | **0.67x / 0.87x** | **1.97x / 0.52x** |
| scatter | `947dfa0` | 8GB, 32 threads | 43/43 | 103.4 | 1.778 | 132.7 | 1.17x / 1.37x | 3.43x / 0.81x |
| single | `26794eb` | 1GB, 16 threads | 41/43 | 71.3 | 0.675 | 129.3 | 0.69x / 1.03x | 2.07x / 0.60x |
| scatter | `26794eb` | 1GB, 16 threads | 42/43 | 170.4 | 2.302 | 213.5 | 1.56x / 1.92x | 4.64x / 1.12x |

- **single:** `"distributed": false`. Every query runs in query-0's job
  engine: one c6a.4xlarge.
- **scatter:** queries that decompose run as partials on all 3 query pods
  (48 vCPU, 20 GB workers) and merge in query-0's job engine.
- `947dfa0` adds T-631 (`SMOLQUERY_JOB_MEMORY_LIMIT`, set to 8GB) and T-630
  (each shard decides its own file cache), and the deploy raised threads to
  32 (`smolquery-deploy/deploys/2026-10-04_03_main-947dfa0-shard-cache-and-job-memory.md`).

## Findings

1. **8 GB fixes every failure.** Q23, Q34 and Q35 ran out of memory in the
   1 GB engine ("Out of Memory Error: failed to allocate data of size
   16.0 MiB (939.5 MiB/953.6 MiB used)"). On 8 GB all three pass: Q34 and
   Q35 in 3.8 to 3.9 s. Q33 drops from 20.6 s to 5.6 s on one engine, and
   from 47.5 s to 17.1 s scattered. Q19 drops from 8.2 s to 2.8 s.
2. **Scatter is still slower overall: 103.4 s against 57.6 s.** The scatter
   probe (ClickBench Q2, 672 bytes of partials) measured **1.45 s of fixed
   overhead per scattered query**: 0.33 s single against 1.78 s scattered,
   median of 9 hot tries. 24 of 43 queries scatter, so the fixed cost alone
   is about 35 s.
3. **One query gains from scatter:** Q29 (`REGEXP_REPLACE`, CPU-bound)
   scatters on `947dfa0` and takes 5.8 s against 9.2 s on one engine. It
   did not scatter on `26794eb`. The other queries that came out faster
   with scatter did not scatter in that pass; they differ by about 10%,
   which is run-to-run noise.
4. **Cold is faster with 32 threads.** The single pass's cold sum fell from
   129.3 s to 94.2 s: the thread count is also each scan's S3 request
   concurrency. Q3 cold: 6.0 s at 16 threads, 2.2 s at 32.
5. **The slowest single-engine queries** are Q29 (9.2 s), Q33 (5.6 s), Q35
   (3.9 s) and Q34 (3.8 s): 22.6 s of the 57.6 s.

## Setup

- smolquery `main@947dfa0`, image
  `sha256:fd28deac56972dfd04c97a731da4253d35a83c80c8a5aa8774cfd5b84a74e893`
  (earlier passes: `main@26794eb`, `sha256:50d1b1b5…`).
- **Query tier:** 3 pods, each alone on a c6a.4xlarge (16 vCPU, 32 GiB).
  Pod limit 28 GiB. 300 GB gp3 root at 6,000 IOPS and 500 MB/s for
  `/cache` and `/spill`
  (`smolquery-deploy/overlay/sandbox/patch-query-dedicated.yaml`).
- Ingest tier unchanged: 3 api pods on m7i.large, 3 buffer and 3 storage
  pods on m7i.xlarge.
- Table `bench.hits_v2`: 105 columns, integers as `INT64`, text as
  `STRING`. Clustering `[CounterID, EventDate, UserID, EventTime]`.
- Queries: ClickBench `duckdb/queries.sql` with the table name changed.
- The network adds about 4 ms per query (median client wall time minus the
  server's `durationMs`). The server's own floor is about 0.2 s per query:
  the published entries time the query in the engine's own client, with no
  HTTP and no job setup.

## Ingest

| metric | value |
|---|---|
| rows | 99,997,497 accepted, 0 rejected, 0 failed |
| time | 680.8 s (conversion and upload; Parquet download excluded) |
| rate | 146,882 rows/s, 323 MiB/s (NDJSON, ~2.3 KB/row) |
| shape | 8 pipelines (`DuckDB COPY TO /dev/stdout \| upload1brc`), 6 workers each, 48 requests in flight, ~4,000 rows (~9 MB) per request, 24,070 requests, 3 api pods |
| ack latency | worst pipeline p50 1.26 s, p99 2.26 s |
| 429s / retries | 0 / 0 |
| hot-tier drain | 68 s |
| `count(*)` | 99,997,497 (exact) |

The load did not saturate the cluster. Mid-load, the buffer pods used
1.0 to 1.2 cores and the storage pods 0.8 to 1.3 cores, on 4-vCPU nodes.
Unsealed bytes held at 40 to 60 MB per buffer pod. More pipelines would
probably go faster. The published datalake entries have no load step.

## Next steps

- Find the 1.45 s fixed cost of the scatter path, or skip scatter for scans
  a single engine finishes faster.
- Size job threads from the pod's CPU and the jobs in flight: 32 threads
  per job oversubscribes a 16-vCPU node under concurrency.

## Reproduce

    LOADGEN_INSTANCE_TYPE=c7i.8xlarge mise run bench-up
    BASE_URL=https://<sandbox-host>:8443 CLICKBENCH_TABLE=hits_v2 \
      CLICKBENCH_FILES=100 CLICKBENCH_COLD=true mise run bench-clickbench

Since 2026-10-04 one run does both passes, the scatter probe and the report.
The passes above came from separate runs, each with one mode
(`CLICKBENCH_QUERY_OPTIONS` carried `"distributed"`). The probe numbers come
from `results/raw-loadgen/loadgen-clickbench-hits_v2-livecheck.clickbench.json`.

Raw data in `results/raw-loadgen/`: `loadgen-clickbench-hits_v2{,-single,-947-single,-947-scatter}.clickbench.json`,
with a `*.metrics.sqlite3` and an HTML report per run.
